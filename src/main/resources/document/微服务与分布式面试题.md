# 微服务与分布式面试题

#### 微服务相比单体有哪些优缺点？
微服务把大应用拆成按业务边界划分、独立开发部署运行的小服务，各自独立数据库，服务间 HTTP/RPC/MQ 通信。优点：独立部署、技术栈灵活、故障隔离、可独立伸缩、团队边界清晰。缺点：运维复杂、网络延迟与一致性问题、排障链路难、测试成本高。小项目上微服务常是过度设计。

#### 什么是服务注册与发现？常见实现？
注册中心维护「服务名 → 地址列表」。服务启动注册自己（含 ip:port 和健康状态），消费方按服务名拉取实例做负载均衡，下线或心跳失败被剔除。常见：Eureka（AP）、Nacos（AP/CP 可切，兼配置中心）、Consul、Zookeeper（CP，强一致但性能弱）。

#### 熔断、降级、限流有什么区别？
熔断：下游连续失败达阈值跳闸，短时间快速失败保护自己，再半开试探恢复。降级：资源紧张时牺牲非核心保核心（如双十一关推荐、返回兜底）。限流：主动控制流量，算法有固定/滑动窗口、漏桶、令牌桶（Sentinel 常用）。

#### 分布式事务有哪些方案？优缺点？
1）2PC/XA 强一致但同步阻塞、单点、性能差；2）TCC（Try/Confirm/Cancel）最终一致、并发好，但侵入业务、需处理幂等/空回滚/悬挂；3）本地消息表/事务消息用 MQ 保证最终送达，解耦但有延迟；4）Saga 长事务拆链路反向补偿；5）AT 模式（Seata）自动回滚无侵入但依赖数据源代理。强一致才考虑 XA，多数用「消息 + 最终一致」或 TCC。

#### 如何设计全局唯一分布式 ID？
1）数据库自增/号段模式，简单但单点；2）UUID 本地生成无中心但无序、占空间、不适合主键；3）雪花算法 64 位 = 符号位 + 41 位时间戳 + 10 位机器码 + 12 位序列号，趋势递增高性能，依赖时钟（回拨会重复）；4）网易 Leaf 号段+双 buffer、百度 UidGenerator 等工程方案。要点：唯一、递增、低延迟、高可用。

#### 什么是 CAP 定理和 BASE 理论？
CAP：一致性、可用性、分区容错三者不能同时满足，网络分区不可避免，只能在 C/A 间权衡。CP（ZK、强一致 MySQL）分区时牺牲可用；AP（Eureka、多数 NoSQL）优先可用、允许短暂不一致。BASE 是 AP 落地：基本可用、软状态（允许中间态）、最终一致。

#### 消息队列典型场景？如何保证不丢失和幂等？
场景：异步削峰、解耦、流量削峰。不丢失：生产端 confirm 确认；MQ 持久化；消费端手动 ack 成功才提交。幂等：网络重试会重复消费，用唯一业务 id（订单号+事件类型）去重表/唯一索引或状态机，保证重复执行结果一致。

#### Redis 和 Zookeeper 分布式锁的区别？
Redis 用 SET NX PX + Lua 释放，性能高、轻量，但基于过期时间、主从异步复制下可能丢锁，严格场景 Redlock 仍被质疑；ZK 用临时顺序节点 + watch，客户端宕机临节点自动删除释放锁，一致性更强（CP），但性能低、运维重。高并发容忍极小概率丢锁用 Redis，要求高可靠用 ZK/etcd。

#### 如何实现接口幂等性？
幂等 = 同样请求执行一次和多次结果一致。手段：1）唯一请求号 + 数据库唯一索引/去重表；2）乐观锁版本号 CAS；3）状态机限制（已支付不重复支付）；4）token 防重复提交；5）MQ 消费端业务 id 幂等。核心是给每次操作唯一标识 + 落库唯一约束兜底。

#### 什么是服务雪崩？如何预防？
某服务故障或响应变慢拖满调用方线程，连锁拖垮上下游直至系统不可用。预防：超时控制、熔断快速失败、线程池/信号量隔离（Hystrix/Sentinel）、限流降级、谨慎重试（配合退避）、依赖弱化兜底（本地缓存）。核心是「快速失败、不让故障扩散」。
